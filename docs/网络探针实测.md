## 2. 拿报告

```text
ux0:data/yunyin-netprobe.log      ← 探针的完整报告（每行一条事实）
ux0:data/yunyin.log               ← 同一批内容也会以 [net] 前缀进主日志
```

报告里每一轮都长这样：

```text
NET attempt   [range/206 on API host] tls=default range=bytes=0-2047 url=...
NET result    status=206 bytes=2048 cl=... range=0-2047/... audio=... redirected=0 headers=... took=...ms
NET payload   first=49443304 magic=MP3(ID3)
NET verdict   [range/206 on API host] range206=true body=true PASS
```

失败时会多一行：

```text
NET error     stage=send code=0x80436002 RESOLVER_ENODNS (DNS)
NET tls       ssl_error=0x80435060 detail=0x00000000
```

| 字段 | 含义 |
| --- | --- |
| `stage` | init / create / send / status / read / abort —— 卡在哪一步 |
| `code` | Vita 原始错误码（已附人类可读名，DNS/TLS/超时/取消都能区分） |
| `range206` | 是否真的返回 206 且带 Content-Range |
| `abort stop_after_abort=…ms` | 调用 `sceHttpAbortRequest` 后多久真正停下 |
| `NET memory` | SceHttp / SceSsl 内存池用量与峰值（§27 的内存结论就靠它） |

## 4. 验收清单（任务书 §26）

| 项 | 报告里看哪一行 |
| --- | --- |
| DNS | `NET error … RESOLVER_ENODNS`（没这行说明 DNS 通过） |
| HTTPS 握手 | `NET result status=<非 0>` 且无 `NET error stage=send` |
| 证书校验 | `tls=verify` 那一轮：`status=206` 通过；`HTTPS_CERT` 即证书被拒 |
| 302 | `redirected=1` 且 `status=206` |
| Cookie / Referer | `cookie header reaches server` 那一轮返回 206 |
| Range / 206 | `range206=true` |
| Content-Length | `cl=`（不是 -1） |
| Content-Range | `range=0-2047/…` |
| 取消 | `NET abort … aborted=1 stop_after_abort=<1000ms PASS` |
| 网络权限 | 上面任何一项通过即说明 `ATTRIBUTE2=12` 够用；全部 `stage=init` 失败则说明不够 |

## 5. 已经踩过的坑（别重复）

第一次真机跑的时候，探针其实**已经把要测的都测到了**（DNS/TLS/206/Content-Range 全过），
但随后整个应用崩溃，dump 显示 PC 落在 newlib 的 `_svfprintf_r`：

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 把 `sceHttpGetAllResponseHeaders` 返回的指针 `free()` 了 | 那是 SceHttp 内存池里的指针，释放会破坏库的堆，之后任何 printf/malloc 都可能跑飞 | **只读，不释放**；它随请求一起失效 |
| 用 `printf("%.150s", value)` 打印头部 | 那个块**不保证 NUL 结尾**，`%s` 会读过头缓冲区的尾端 → Data abort | 一律用 `%.*s` + 长度，扫描也按 `headerSize` 限界 |
| 把 `sceKernelStartThread` 的参数当成"共享结构体" | 该 API 会把参数**拷贝**到新线程栈上，主线程看到的永远是原结构体（全 0）；后来改成 `argp=NULL` 却还在 worker 里解引用 → 写地址 0，`DFAR=0x0` | 线程间共享状态用**静态/堆**结构体，`sceKernelStartThread(thid, 0, NULL)` |
| abort 后立刻删除请求 | worker 可能还在那次读里，删掉请求等于抽掉地板 | 等 worker 退出再删；没退出就**宁可泄漏也不删** |

两条都已经写进 `native/net/yhttp.c` 的注释里，Phase 2 的 `HttpRangeSource` 也要遵守。

| 额外注册根证书 | 做不到，但不影响 | `sceHttpsLoadCert(47)` 在 ssl/http = 256K→512K→1M→2M 四档全部 `0x80431022`（OUT_OF_MEMORY），而 2 MB 的 http 池实际只用了 912 B —— 它不是从这两个池分配；该 API 只是"额外注册根证书"，默认校验不依赖它 |

关于证书校验的处置（Phase 2 必须明确写下策略）：

* 参考项目 vitaspotify 用 libcurl 时直接 `CURLOPT_SSL_VERIFYPEER=0` /
  `VERIFYHOST=0`，即**不做证书校验**；这是该平台 homebrew 的普遍做法。
* **实测结论：这台机器的 SceHttp/SceSsl 默认就校验证书** —— 自签名与过期证书主机都被
  拒绝（`SCE_HTTP_ERROR_SSL` / `0x80431075`）。所以 YUNYIN 的 HTTPS 是**加密 + 校验**，
  比参考项目更严（它们是不校验）。
* 因此 Phase 2 的策略定为：**API 跳走 HTTPS（默认校验开着，什么都不用额外做）**；
  音频 CDN 跳是明文 `http://`（实测），照常带 Referer 即可。
* 探针每轮仍会跑那两个坏证书目标：一旦哪天返回 200，说明校验被关掉了，日志会直接
  显示 `cert-reject=false … CHECK`。

### 6.1 两种"开校验"的方式不是一回事（00.70 起）

```c
/* 真正把检查打开：进程级，没有 id 参数 */
sceHttpsEnableOption(SCE_HTTPS_FLAG_SERVER_VERIFY   /* 0x01 */
                   | SCE_HTTPS_FLAG_CN_CHECK        /* 0x04 */
                   | SCE_HTTPS_FLAG_NOT_AFTER_CHECK /* 0x08 */
                   | SCE_HTTPS_FLAG_NOT_BEFORE_CHECK/* 0x10 */
                   | SCE_HTTPS_FLAG_KNOWN_CA_CHECK);/* 0x20 */

/* 只是"额外注册根证书"；这台固件上必然 OOM，失败也不代表校验关着 */
sceHttpsLoadCert(...);
```

00.70 起 verify 模式两个都做：先 `sceHttpsEnableOption` 打开五个检查（结果记进
`flags=0x…`），再尝试加载 CA（结果记进 `ca=0/1`）；**判定交给
`self-signed.badssl.com` / `expired.badssl.com` 这两个目标**——它们被拒绝才算校验真的生效。

### 6.2 加载根证书会重建网络栈，绝不能在播放时做（00.76 起）

00.75 的真机日志里出现过一次很难看的现象：

```text
remote: 流已打开 size=Some(3863085)          ← 在线流已经拿到第一个窗口
[net] yhttp: sceHttpsEnableOption(0x3D) ...  ← 探针线程的 verify 目标进来了
remote: read 失败 Cancelled
remote: read 失败 Cancelled
yplayer: 解码器打不开这份流（格式认不出或解码器失败）
```

原因不是解码器：`yhttp_load_ca()` 为了把根证书装进更大的池子，走了
`sceHttpTerm() + sceSslTerm()` → 调大池子 → `sceHttpInit() + sceSslInit()`。
**这套栈是进程级的**，重建的那一刻，音频线程手里那个正在读 MP3/AAC 字节的请求
当场作废。而 `yhttp_load_ca()` 之前既不记"试过了"，也不看有没有流在用，于是每跑
一轮探针就拆一次栈。

00.76 的处置（都在 `native/net/yhttp.c`）：

| 规则 | 原因 |
| --- | --- |
| 根证书装载**只试一次**（`g_ca_tried`） | 这台机器任何池大小都装不进去，反复重试只有坏处 |
| 有在线流在用网络栈时**推迟**（`g_streams_open > 0`） | 重建栈 = 抽掉音频线程脚下的地板 |
| 取窗口失败**允许重试 3 次**，`s->err` 不再永久粘住 | 一次连接抖动不该把整首歌判死 |
| HTTP **416 当成"到尾"**，不写错误 | 解码器探测长度时会问到越界偏移，那不是故障 |

### 6.3 「探过一次尾巴」≠「整条流结束」（00.77 起）

00.76 装上真机后还是不出声，日志里只有一条线索：解码器探测完文件尾巴（读 ID3v1），
紧接着就报"解码器打不开"，中间**再没有任何一次窗口请求**。

在电脑上把这条链原样搭出来（`ysim2`：C 侧窗口 + Rust 侧窗口 + 真 mpg123 + 真文件，
HTTP 换成读本地文件）之后，一眼就看到：

```text
[C] 窗口请求 off=3600349 -> len=128            ← 解码器探测尾巴（SEEK_END -128）
[C] read(off=3600349) -> 128
[seek] off=0 -> 0                              ← 探完回到开头
[C] read(off=0 n=262144) -> 0                  ← ★ 开头竟然返回"结束"
** 解码器打开失败
```

根因是**两层各有一个"我们见过流末尾了"的陈旧标记**，被当成了整条流的状态：

| 层 | 陈旧标记 | 后果 |
| --- | --- | --- |
| C（`yhttp_stream_read`） | `if (s->eof && s->win_len == 0) break;` | 416 会把窗口清空，于是"探过尾巴"变成"整条流结束"，连 off=0 都返回 0 |
| Rust（`HttpRangeSource`） | `wait_for()` 里的 `w.eof` | 上一个位置到过底，之后换位置取数会被这个旧结论挡住 |

两者的修法一样：**"到底"只对"这一次请求的那个位置"成立** ——
C 侧删掉那句提前收工、只看本次取回的窗口是否为空；
Rust 侧在登记新请求（`request_from` / `wait_for` / 取数线程开工）时清掉 `w.eof`。

验证方式（都在电脑上，`ysim2`）：让六个格式**全部走在线这条链**跑完整解码，
PCM 校验和与本地基线逐位一致（MP3/OGG/FLAC/WAV/OPUS 五项；M4A 是硬件 AAC，
电脑上没有解码器，只能验到解复用）。修之前，同一台子上连 MP3 都打不开。

顺带得到的数字：整首 3.6 MB 的 MP3 只发了 18 次 Range 请求（约每 200 KB 一次），
窗口策略没有被这次修复改坏。

### 6.4 「末尾」是一个位置，不是一个布尔（00.78 起）

00.77 上机后仍然是同样的现象，于是把复现台升到**全保真**：真实 `HttpRangeSource`
（真的两条线程 + 条件变量）+ 真实 `yplayer.c` + **和真机同版本的 mpg123 1.33.7**
（VitaSDK 那份自带源码路径 `.../mpg123-1.33.7/src/libmpg123/...`，所以电脑上也编了一份同版本）
+ 真文件。A/B 一跑就分出了真假：

```text
A（把"换位置时清理旧标记"去掉）:  尾部读 -> Err(WouldBlock)  → 解码器不回开头、卡在尾部
B（带清理）:                      尾部读 -> 128 字节         → 正常打开
```

根因是那个标记本身只是个 `bool eof`（"我们见过一次末尾"），而解码器的行为是
「先到末尾、再回前面读」—— 于是这个陈旧的 true 会立刻告诉它"这里没数据"，
解码器拿到负返回值就**再也不回开头**了，从此卡在文件尾部空转（日志里那 700 多行
"窗口没盖住请求偏移"）。

00.78 把语义一次改对（`native/rs/source/http.rs`）：

| 以前 | 现在 |
| --- | --- |
| `eof: bool` —— "见过末尾" | `end_at: Option<u64>` —— "**从哪个位置起**没有数据了" |
| `wait_for()` 见到 `eof` 就立刻回"没数据" | 只有你要的位置**已经过了那个点**才算结束 |
| 一次等不到就返回 | 打开阶段最多等 3 轮（约 12 秒），首包慢一点也不会被判成硬错误 |

另外两处配套修正：

* `native/net/yhttp.c`：请求位置已经在流末尾之外时，**连窗口一起清空**再返回，
  这样"窗口没盖住请求偏移"那条错误分支不会再被触发（它以前会写 `s->err = -1`）。
* `native/rs/mod.rs`：启动日志第一行写出版本号（`yunyin: start ... 版本 00.78`）。
  这一轮排障白花了整整一次往返就为了确认"机上装的是哪一版"，以后直接从日志看。

全保真复现台回归：七种文件（含网易云那份真 MP3）全部打开并解码；六格式 PCM 校验和
与基线一致（MP3 那项与电脑自带 mpg123 1.32.5 的基线差 1 个采样，是解码器版本差异，
不是本改动引起 —— 与真机同版本的 1.33.7 上反而是它自己的一致值）。

### 6.5 窗口不能因为"别人问了别的位置"就被清掉（00.79 起，未上机）

00.78 上机后的新现象：**同一段尾部 128 字节被反复用 HTTP 下载**（一次约 50 ms，
共十几次），然后解码器报"打开失败"：

```text
[net] yhttp: stream 窗口 0..262144（262144 字节，总长 3863085）
remote: 流已打开 size=Some(3863085)
[net] yhttp: stream 窗口 3862957..3863085（128 字节，总长 3863085）   ← 第 1 次
[net] yhttp: stream 窗口 3862957..3863085（128 字节，总长 3863085）   ← 第 2 次
... 共 10 次 ...
yplayer: 解码器打开失败 fmt=1（嗅探=1）
```

原因在 `HttpRangeSource` 的缓存策略上：**每次登记新请求都会先把窗口清空**。解码器
打开文件时固定会做一次"跳到末尾问长度"，那一问就把刚缓存的尾部窗口清掉了；它回头
再读尾部，窗口已经是空的 → 只能重新发一次 HTTP，把同一段 128 字节再下载一遍。

用真实 `HttpRangeSource`（不是移植版）跑一个最小对照，看得非常直接：

```text
动作（重复 3 次）: seek(文件末尾) → seek(末尾-128) → read(128)

00.78: 传输层调用 7 次 = [0, 3863085, 3862957, 3863085, 3862957, 3863085, 3862957]
       —— 末尾和尾部交替出现：每问一次长度，尾部就得重下一遍
00.79: 传输层调用 5 次 = [0, 3863085, 3862957, 3863085, 3863085]
       —— 尾部只下载了一次
```

改法（`native/rs/source/http.rs`）：**请求新位置只登记"下次抓哪儿"，不动已有缓存**；
只有真的抓到新数据时才整体替换窗口。抓不到（越界/失败）时旧窗口依然有效。

### 6.6 真凶：等待超时那一刻又登记了一次请求，把正在飞的抓取作废了（00.80 起）

00.79 上机时内置了取数层轨迹（`netdbg`），一次就看清了：

```text
netdbg#9  read 入口 pos=3862957 want=128
netdbg#10 登记取数 pos=3862957 generation=4
[net] yhttp: stream 窗口 3862957..3863085（128 字节）        ← HTTP 抓到了 128 字节
netdbg#11 取数作废 from=3862957 got=Ok(128)（抓取期间登记了新请求）   ← ★ 被丢掉
netdbg#12 登记取数 pos=3862957 generation=5
netdbg#13 登记取数 pos=3862957 generation=6                ← 同一个等待里又登记一次
netdbg#14 等 pos=3862957 超时（窗口=[3862957,3862957) pending=true） ← 窗口已被清空
... 同样的一幕重复十几次 ...
netdbg#29 read 等不到数据 -> WouldBlock → 解码器打开失败
```

**每一次抓取都成功，每一次都被下一次登记判为过期丢掉** —— 于是无限重下同一段，
直到 `read()` 用完 3 轮等待预算（12 秒）返回负值，解码器把它当硬错误。

三个原因叠在一起，都在 `wait_for()` / 取数线程这一对里：

| 问题 | 后果 |
| --- | --- |
| 取数线程一开工就把 `pending` 置回 false，"有人在抓"看不出来 | 消费端在等待里被唤醒时以为没人管，**又登记一次** → 代数 +1 → 把在飞的抓取作废 |
| 登记写在超时判断**之前** | 超时返回那一刻也登记一次，留下一个没人等的请求，下一轮再登记一次 |
| 登记时清空窗口 | 抓到的字节被丢掉之后连旧数据也没了，窗口变 `[pos,pos)` 空的 |

改法（`native/rs/source/http.rs`）：

* 窗口增加 `inflight`：取数线程**正在抓**时消费端绝不重复登记（这才是"有人在干活"的真标志）；
* `wait_for()` 里**先判超时、再登记**，超时不再留下垃圾请求；
* 登记与作废都不再清窗口（数据只在真的抓到新内容时才整体替换）。

电脑上的定量对照（同一个假传输，尾部那一次抓取故意用 5 秒，比单轮等待上限 4 秒长）：

```text
修复前: 尾部读 -> Err(WouldBlock)（12000 ms），传输层 3 次 [0, 3862957, 3862957]（两次都作废）
修复后: 尾部读 -> Ok(128)（5000 ms），  传输层 2 次 [0, 3862957]（一次，交付成功）
```

### 6.7 解码回调里不许写日志（00.81 起）

00.80 上机：上面那条链终于通了 —— 真机日志里出现

```text
netdbg#10 取数 from=3862957 got=Ok(128) 已发布      ← 尾部只下一次，零作废
yplayer: open via yp_io fmt=1 hint=0 sniff=1 size=3863085 rate=48000 ch=2
remote: 解码器已接上在线源                          ← 打开成功
```

但**紧接着进程 Data abort 崩掉**（`DFAR=0xc`）。把崩溃地址按"ELF 基址 + 偏移"符号化
（基址 = PC 绝对值 − dump 里的 +偏移，这次是 0x8105d000）：

```text
#0 <core::fmt::Formatter>::pad        ← Rust 在拼字符串
#1 mp3_io_read                        ← 我们的 mpg123 读回调
#2 <String as Display>::fmt
#3/#4 wrap_read   #5 plain_fullread   #6 generic_head_read   #7 INT123_read_frame
```

即：**解码器读数据 → 我们的 IO 回调 → 里面做了一次字符串格式化 → 崩**。罪魁是 00.79
为了排障加的"每次读都写一行 netdbg"。播放阶段这些读在**音频线程的解码回调**里，
那里不该拼字符串、也不该动文件系统（`DFAR=0xc` 是 trait 对象被打坏的样子，典型的栈被压穿）。

00.81 的规矩（以后写这块代码都照这个来）：

| 位置 | 允许做什么 |
| --- | --- |
| 解码回调（`io_read`）/ `HttpRangeSource::read` | **只做原子计数**；轨迹只在打开阶段开（`trace_off()` 在解码器接上后立刻调用），且用闭包版 `trace_f` 保证不写日志时连字符串都不拼 |
| 打开阶段（`yp_open_io` 前后） | 可以写轨迹，但上限 400 行 |
| 收尾（`close_remote`） | 打印一行计数汇总 |

顺带把栈加厚：音频线程 64 → 128 KiB，在线打开线程 64 → 96 KiB。

### 6.8 真凶：日志文件被多线程并发写，把 stdio 和堆踩坏了（00.84 起）

00.83 加的面包屑把崩溃位置钉死了 —— 日志最后几行是：

```text
152: yplayer: open via yp_io fmt=1 hint=0 sniff=1 size=3863085 rate=48000 ch=2
153: remote: 解码器已接上在线源
154: dbg: 在线源已接上，取格式
155: dbg: 取时长（mpg123_length 会扫流）
156: dbg: 时长已取到
157: dbg: 起音频口
158: dbg: 音频线程第一拍dbg: 音频口已起      ← ★ 两行日志黏在一行了
```

最后一行之后就是 `log::append(&format!("bgm: play_url {url} …"))`，它**从未出现** —— 崩点就在这句。

而第 158 行是**决定性证据**：**音频线程和在线打开线程在同时写同一个日志文件**
（两行黏在一起 = 写了一半被另一条线程插进来）。两条写日志的路径还完全不同层：

| 谁 | 怎么写 |
| --- | --- |
| C 侧 `host/yunyin_log.h` | `sceIoOpen / sceIoWrite / sceIoClose` |
| Rust 侧 `platform/log.rs` | `std::fs::OpenOptions` + `writeln!`（newlib，`open` 会 malloc 一个 FILE 挂进全局表） |

**两条路径之间没有任何互斥。** 在线播放让日志变成多线程并发写（音频线程 / 在线打开线程 /
取数线程 / 界面线程），底层 stdio 的 FILE 表与堆被踩坏；之后的崩溃点就变成"随手一次字符串
格式化"（`DFAR=0xc`，格式化用的 trait 对象被踩成 0）—— 所以修过两次"格式化"都没修到点子上。
本地播放之所以从来不崩：那时候几乎没有别的线程在同时写日志。

00.84 的修法：**所有日志共用一个锁**。

* `platform/log.rs` 加 `LOG_LOCK`，`append()` 先拿锁再 open/write/close；
* 新增 `yunyin_log_line()`：C 侧 `yunyin_log()` 不再自己 sceIoWrite，改为调它，走同一把锁；
* 探针报告文件（`report()`）也走同一把锁（它同样可能被取数线程和探针线程同时写）。

这条经验值得记住：**日志是共享资源**。在 Vita 上，跨线程并发 open/write 同一个文件
不是"行会交错"这么轻，而是会把 stdio 和堆一起踩坏。

### 6.9 Gate / 预取 / 重试：让长曲子连着播完（00.86–00.88）

00.87 真机已经能播，但**播到 28 秒停住**：日志里 `remote: 缓冲不足，先静音（剩 63 KB）`
之后再没有任何窗口请求。数字正好对上 —— 首窗 16 秒 + 第二窗 16 秒 − 触发阈值的 4 秒 ≈ 28 秒。

三层原因（都在"Source 层 ↔ Gate"的配合上）：

| 原因 | 说明 |
| --- | --- |
| **Gate 死锁** | Gate 是在"剩余不足 64 KiB"时静音的，那时位置**还在窗口里**；而静音这条路当时没有登记取数 → "没人拉数据 → 永远没数据 → 一直静音" |
| **预取断链** | 预取槽升格成当前窗口后槽空了，却没人补下一窗 → 下次跨窗又要等一次完整 HTTP（真机 1.8–2.7 秒） |
| **瞬时失败被粘死** | 取数失败一次就把错误设成粘性，之后取数层直接返回不再尝试 —— 网络抖一下这首歌就永远起不来 |

修法（`native/rs/source/http.rs` + `remote.rs` + `bgm.rs`）：

| 规则 | 原因 |
| --- | --- |
| 窗口做成**双缓冲**：取数线程每发布一窗就顺手把下一窗也抓进来；跨窗时"升格"预取槽 | 缓存里始终留一窗（≈16 秒）余量，跨窗不再等 HTTP |
| Gate 静音时调用 `prime()`，判据是**提前量够不够**（不是"位置被盖住没有"） | 静音那条路必须也去拉数据，否则就是死锁 |
| 失败改成**连续 4 次**才判死，中间退避 300 ms 重试；抓到数据就清零 | 网络抖一下不该让整首歌报废 |
| Gate 增加"**末尾放行**"（`at_cached_end()`）：缓存接到已知末尾就让解码器收尾 | 文件最后一段本身就不足阈值，不放行会卡在结尾 |

验证（电脑，真 Rust 双线程 + 真 mpg123 1.33.7 + 网易云那份真文件 + **Gate 模型**）：

```text
正常链路：整曲 241 秒（11585280 帧）解完，静音块 0、抓窗口 20 次、最终失败 0 次
慢网络 + 每 4 次注入一次瞬时失败：自动退避重试后继续播（旧逻辑会就此卡死）
```

> 台子上的两个注意点：**它解码得比实时快约 100 倍**，所以给传输层加人为延迟时，
> 「静音块」统计只说明"网络跟不上这个超快的消费者"，**不能**当成真机断流指标 ——
> 真机是实时播放（一窗 ≈ 16 秒音频，一次请求 1.8–2.7 秒，余量充足）。
> 台子的价值在**正确性**：不卡死、能跨窗、能重试、能收尾。

真机（00.88）：**整首 4 分 01 秒完整播完**，进度与时长正常，日志无静音行。Phase 2 闭环。

**给以后的规矩**：音频线程的"静音"永远不能是终点 —— 静音的同时必须有人去拉数据。
这类死锁在电脑上很难自然复现，所以复现台要把 Gate 也一起建模（见 §8.5 的工具清单）。
