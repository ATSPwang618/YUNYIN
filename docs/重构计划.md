## 五、十个关键问题（答案都来自源码或实测，不猜）

1. **六个 decoder 是否支持 callback IO？** 是。mpg123：`mpg123_replace_reader_handle`；
   vorbisfile：`ov_open_callbacks`；dr_wav：`drwav_init(onRead,onSeek,userdata)`；
   dr_flac：`drflac_open(onRead,onSeek,userdata)`；opusfile：`op_open_callbacks`；
   M4A：`ym4a.c` 是自己写的，需要改成 `yp_io`。
2. **callback 能表达 WouldBlock 吗？** 不能。各库的读回调以 0/短读表示
   EOF 或错误，没有「稍后再来」的语义。
3. **那怎么避免 decoder 看到「暂时没数据」？** 用 **Gate**：`available() < decode_margin`
   时音频线程不调用 decoder，直接输出静音；缓存补到水位以上才恢复。这样
   decoder 永远不会因为「网络慢」而结束播放。
4. **`MPG123_FORCE_SEEKABLE` 在远端怎么办？** 它会让 mpg123 扫描整条流来确定长度
   （头文件原文：无法确定大小时「stream is assumed as non-seekable unless overridden」）。
   远端做法：不设该 flag，改为 `mpg123_set_filesize(Content-Length)`，seek 交给我们的
   回调完成；本地文件保持现状。
5. **网络时长不可靠时怎么给 duration hint？** Provider 的 `AudioInfo.duration_ms` 先给
   UI 用；解码器就绪后以其自报时长覆盖。M4A 的时长来自容器样本表，天然可靠，
   可作为对照。
6. **没有扩展名如何识别格式？** `AudioFormat::sniff(head)`（已实现、已用六个真实文件
   验证，含 M4A 的 `ftyp`）。
7. **URL 过期如何重新获取？** `UrlCache` + `EXPIRY_MARGIN_MS`；传输层拿到
   403/404/410 时 `invalidate(song_id)`，重取一次并重试。
8. **切歌如何取消 HTTP？** `HttpClient::cancel` + `RangeFetcher::cancel`
   + `SourceError::Cancelled`；用会话序号（generation）丢弃迟到的响应。
9. **Vita 实际网络内存需要多少？** 待实机验证：Phase 0 打印 socket/TLS 缓冲与
   可用堆，再决定 512 KiB / 1 MiB / 2 MiB。
10. **`ATTRIBUTE2=12` 是否足够网络播放？** 待实机验证（Phase 0 第一件事）。

### Phase 2 进展（00.76）

链路已经全部接上：`在线 URL → yhttp_stream_*（C）→ Stream/HttpRangeSource（Rust）
→ yp_io → 解码器 → BGM 口`。00.75 真机上"流打开了、解码器却打不开"的两个原因都已定位并修掉：

| 问题 | 真相 | 修法 |
| --- | --- | --- |
| 解码器打开失败 | 探针线程加载根证书时 `sceHttpTerm/SceSslTerm` **重建了整个网络栈**，音频线程正在读的请求当场作废 | 根证书只试一次；有在线流在用就推迟（见 [网络探针实测.md §6.2](网络探针实测.md#62-加载根证书会重建网络栈绝不能在播放时做0076-起)） |
| 读一次就"到尾" | `is_eof()` 用了"抓取线程报过 eof"，而解码器探测长度时会 seek 到远处，那次越界被永久当成结束 | 长度已知时 `is_eof = pos >= size`；HTTP 416 只当"到尾"，不当错误 |
| **还是打不开**（00.77） | 解码器探测完尾巴会 seek 回开头，而两层各有一个"我们见过末尾"的旧标记把整条流判死 → off=0 的读返回 0（假 EOF） | "到底"只对本次请求的位置成立（[网络探针实测.md §6.3](网络探针实测.md#63-探过一次尾巴整条流结束0077-起)） |
| **仍然卡在尾部空转**（00.78） | 那个标记是 `bool`（"见过末尾"），而解码器的行为是"先到末尾、再回前面读" → 陈旧 true 让它拿到负返回值、**再也不回开头** | 改成 `end_at: Option<u64>`（末尾是一个**位置**）；打开阶段最多等 3 轮；见 [§6.4](网络探针实测.md#64-末尾是一个位置不是一个布尔0078-起) |

界面这一轮只做了最小的一步：**在线曲目是曲库里的独立条目**（专辑「在线歌曲」），
点它、按 ○ 才走网络；本地歌曲的位置一个都没被动过。缓冲状态与错误提示留给 Phase 5。

### 8.3 已定位的真凶（00.79 的 netdbg 轨迹 + 电脑复现，已修）

00.79 上机带着轨迹，一次就看清了 —— **每一次抓取都成功，每一次都被下一次登记判为
过期丢掉**（`取数作废 from=3862957 got=Ok(128)`），于是同一段 128 字节被无限重下：

```text
netdbg#10 登记取数 pos=3862957 generation=4
[net] yhttp: stream 窗口 3862957..3863085（128 字节）              ← HTTP 抓到了
netdbg#11 取数作废 from=3862957 got=Ok(128)（抓取期间登记了新请求）  ← ★ 被丢掉
netdbg#12 登记取数 generation=5 / #13 登记取数 generation=6        ← 同一等待里又登记
netdbg#14 等 pos=3862957 超时（窗口=[3862957,3862957)）            ← 窗口已被清空
netdbg#29 read 等不到数据 -> WouldBlock → 解码器放弃
```

三个原因叠在一起，全在"消费端 ↔ 取数线程"这一对里：

1. **取数线程一开工就把 `pending` 置回 false**，"有人正在抓"看不出来 → 消费端被唤醒时
   以为没人管，又登记一次 → 代数 +1 → 在飞的那次抓取作废；
2. **登记写在超时判断之前** → 超时返回那一刻也登记一次，留下没人等的请求；
3. **登记时清空窗口** → 抓到的字节丢掉后，旧数据也没了。

电脑上的定量对照（尾部那次抓取故意 5 秒，长于单轮等待上限 4 秒）：

```text
修复前: 尾部读 -> Err(WouldBlock)（12000 ms），传输层 3 次 [0, 3862957, 3862957]（两次都作废）
修复后: 尾部读 -> Ok(128)（5000 ms），  传输层 2 次 [0, 3862957]（一次成功）
```

**注意**：这台机器上的音频线程在打开阶段根本没参与（`PLAYING=false` 时每 960 帧只输出
静音，从不碰解码器/取数层），所以"两拍"是**同一条消费线程**自己造成的，不是音频线程抢。

### 8.3.1 打开成功之后立刻崩溃：不要在解码回调里做字符串格式化（00.81 起）

00.80 上机：在线流**打开成功**（上面那两行），紧接着进程就因为 Data abort 崩掉
（`DFAR=0xc`，也就是往 `NULL+12` 写/读）。把崩溃栈按"ELF 基址 + 偏移"符号化之后：

```text
#0 pocketjs-vita.elf+0xeffe   → <core::fmt::Formatter>::pad        ← Rust 在拼字符串
#1 pocketjs-vita.elf+0x7c617  → mp3_io_read                        ← 我们的 mpg123 读回调
#2 pocketjs-vita.elf+0x354bf  → <String as Display>::fmt
#3/#4                          → wrap_read (mpg123)
#5                             → plain_fullread
#6                             → generic_head_read
#7                             → INT123_read_frame
```

也就是说：**mpg123 在读数据 → 我们的 IO 回调 → 里面做了一次字符串格式化 → 崩。**
崩溃点正是 00.79 为排障加进去的"每次读都写一行 netdbg"（还有它下面那层 `format!`
与写文件）。播放阶段这些读发生在**音频线程的解码回调里**，那里既不该拼字符串、
也不该动文件系统；`DFAR=0xc` 这种"trait 对象被打坏"的样子也是典型的栈被压穿。

00.81 的处置：

* 轨迹改成**只在打开阶段开**（`trace_off()` 在解码器接上后立刻调用）—— 排障要看的
  本来就是打开阶段；
* 轨迹调用改成闭包版 `trace_f(|| format!(...))`：**不写日志时连字符串都不拼**；
* 解码回调里的错误日志同样走 `trace_f`，播放阶段只记数、不写文件；
* 音频线程栈 64 KiB → **128 KiB**，在线打开线程 64 KiB → 96 KiB（别让解码路径贴着栈顶跑）。

计数（`netdbg 统计: read/seek/fetch/discard/wait_timeout/wouldblock`）保留：只做原子加，
不拼字符串，收尾时打印一行 —— 排障信息不丢，热路径干干净净。

### 8.3.2 00.82 仍然崩在同一个点：格式化那条 60 字节的 URL（00.83 加面包屑）

00.82（去掉日志后）上机**仍然后同一个签名崩**：`DFAR=0xc`、同样的寄存器组合。
把崩溃指令反汇编出来，因果链就非常清楚了：

```asm

8100efbe:  ldr  r3, [r1, #12]    ; ★ 崩在这里：虚表指针 R1 = 0 → 故障地址 0xc
```

| `bgm: play_url {url} rate=… dur=…ms` | `bgm.rs::open_online` 最后一行 | 在线打开线程 |
| 状态 JSON 里的 `"path":"…"` | `bgm.rs::state_json`（界面每 6 帧问一次） | 界面线程 |

### 8.3.3 真凶：日志被多线程并发写（00.84 修复）

00.83 上机，面包屑直接给出答案：最后一行是

```text
157: dbg: 起音频口
158: dbg: 音频线程第一拍dbg: 音频口已起      ← 两行黏在一起 = 两条线程在同时写日志
```

而 158 之后那句 `log::append(&format!("bgm: play_url {url} …"))` 从未出现 —— 崩点就在那里。
两行日志黏在一起是**决定性证据**：音频线程与在线打开线程并发写同一个日志文件。C 侧走
SceIo、Rust 侧走 std::fs（newlib），两条路径毫无互斥；在线播放让日志第一次变成多线程
并发写，底层 stdio 的 FILE 表与堆被踩坏，于是崩溃点表现为"随手一次字符串格式化"
（`DFAR=0xc`）—— 这也解释了为什么前面两次围着"格式化"修都没修到点子上。

修法（00.84）：`platform/log.rs` 加 `LOG_LOCK`，`append()` 与探针 `report()` 都先拿锁；
C 侧 `yunyin_log()` 不再自己写文件，改为调 Rust 的 `yunyin_log_line()`，**全部日志共用同一把锁**。
详见 [网络探针实测.md §6.8](网络探针实测.md)。
